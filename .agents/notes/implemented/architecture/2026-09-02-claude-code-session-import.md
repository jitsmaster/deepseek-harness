# Agent Note: Claude Code session import and skill-derived slash commands

Status: implemented

## Problem

DSH now has a working Claude (Anthropic) route through `llm-pi-ai` (browser OAuth sign-in; see [browser authorization and keyless web search](../../proposed/architecture/2026-09-01-browser-authorization-and-keyless-web-search.md)). A user who also drives Claude Code CLI sessions on the same machine wants to carry a Claude Code conversation into DSH and keep going, without re-explaining context, and wants the same Claude Code Skills they use there available as DSH slash commands once they're working on a Claude-backed DSH session.

Two adjacent asks were considered and rejected before this note:

- **Live-attach into a running `claude --bg` session.** Feasible in principle (`claude agents --json` for discovery/status), but the only ways to read a live session's turns or inject new input are the transcript JSONL (Anthropic's own docs: internal format, changes between releases) and an undocumented cross-session messaging socket. Coupling DSH to both, continuously, for the life of an attached session is a standing maintenance liability against a surface DSH does not control.
- **Byte-perfect structural replay into DSH's session log.** Mapping Claude Code's own tool-call content blocks onto DSH's `SessionEventMap` would require an extensive, version-fragile translation layer and likely a `SESSION_FORMAT_VERSION` bump for a foreign event shape DSH does not own.

## Decision

Two independent, server-side-only capabilities ship. Neither keeps a live connection to Claude Code once its one-shot work is done.

### 1. `claude-session-import` (`packages/session/claude-session-import`, `@deepseek-ai/dsh-claude-session-import`)

A one-time import, not a live bridge:

- **Discovery**: `listClaudeCodeSessions()` shells out to `claude agents --json --all` through `ctx.subprocess.spawn` (stdout capped at 4 MiB, stderr at 64 KiB, a 5s shutdown grace) and maps each raw entry to `DiscoveredSession {id, name, cwd, status, startedAt}` for a new "Import from Claude Code" entry point in DSH's session-creation UI. A `kind: 'background'` entry's `state` (e.g. `done`/`stopped`/`failed`/`blocked`) takes priority over `status` when both are present; a `kind: 'interactive'` entry carries only `status` (e.g. `idle`/`busy`). Entries with a non-UUID id, a non-absolute/empty `cwd`, or an unparseable `startedAt` are dropped with a logged warning rather than trusted downstream (defense in depth: `cwd` seeds the new session's working-directory scope and the id feeds a transcript filename). A missing/unspawnable `claude` binary, non-zero exit, or unparsable stdout all degrade discovery to an empty list, each logged.
- **Import**: `ClaudeSessionImportController.createFrom(sessionId, signal)` maps the chosen session's `cwd` to its Claude Code project directory and reads `~/.claude/projects/<project>/<id>.jsonl` **once**, capped at `RAW_TRANSCRIPT_MAX_BYTES` (800,000 bytes, enforced by a streamed read past `stat()` to close the TOCTOU gap of a CLI still appending to the file). `parseClaudeCodeTranscript`/`renderImportedTranscript` extract user/assistant text turns and render recognizable `tool_use`/`tool_result` blocks as readable text summaries (e.g. "ran `ls -la`, output: …"), capped at 200,000 rendered characters; an unrecognized block degrades to a text summary instead of failing the import.
- **Session creation**: the new DSH session is seeded with the reconstructed turns as opening context and pinned to `IMPORTED_SESSION_MODEL` (`provider: 'anthropic', model: 'claude-sonnet-5'`). From this point the session is fully DSH-native — its own agent loop and tools own everything that happens next. No further contact with Claude Code, the `claude` binary, or the source JSONL.
- **RPC surface**: `ClaudeSessionImportController` (`ctx.claudeSessionImportController`, exposed as `ctx.remote.claudeSessionImport`) exposes `list(signal)` → `ClaudeSessionImportListValue` and `createFrom(sessionId, signal)` → `ClaudeSessionImportCreateValue`, following the `AuthorizationController` pattern from the OAuth feature (`@Remote`/`TypertRemoteService` RPC methods + wire types, no bespoke transport). Two stable `RemoteErrorDetailsMap` codes cover the failure paths: `claude-session-import/not-found` and `claude-session-import/transcript-unreadable`. A 5-minute discovery cache lets `createFrom()` reuse the same picker action's prior `list()` snapshot, falling back to a fresh discovery once that TTL passes.
- **Running/Done grouping in the picker UI**: `groupAndSortSessions()` (`packages/client/ui-session-import`) splits discovered sessions into two sections rather than one flat list — a `running` group and a `done` group, each with an ARIA-accessible section header row in `ImportDialog` — sorted by `startedAt` descending within each section (most recent first). Classification is by a fixed, case-insensitive terminal-status allowlist — `done`, `cancelled`, `completed`, `failed`, `error`, `stopped` — anything not in that set (including a status this codebase hasn't seen yet) defaults to `running`. This allowlist remains a deliberate, not-yet-CLI-verified design choice: `claude agents --json --all`'s status vocabulary is still undocumented, and only `'done'`/`'working'` appear as confirmed real values in this codebase's own fixtures, so the classifier stays intentionally permissive toward "running" rather than risking a session silently vanishing into the wrong bucket.

### 2. `claude-skill-commands` (`packages/interaction/claude-skill-commands`, `@deepseek-ai/dsh-claude-skill-commands`)

- Mounts **per-agent** on `agent/created` (agent-scoped, the same shape `dsh-plan-mode` uses), reading that agent's session `cwd`.
- Scans `<cwd>/.claude/skills/` and `~/.claude/skills/` for `SKILL.md` files via `scanSkillDirectories` and parses each one's frontmatter (`name`, `description`). Project-tier skills shadow user-tier ones of the same name; a skill cannot register over an already-existing command name, including this plugin's own reserved `/refresh-skills` — it is skipped with a logged warning instead.
- Registers one `ctx.commands.register()` entry per skill through the existing `dsh-commands` registry — no new command infrastructure. Invoking `/skill-name [args]` steers the skill body as a `kind: 'plugin'` message (never `kind: 'user'`, so repo-authored skill content is never mistaken for host-attested human input downstream) and, when the operator typed arguments, steers those separately as a `kind: 'user'` message — the same two-message mechanism `/plan [message]` uses for its own body/arguments split. A project-tier skill's body is shown once for confirmation, identity-keyed by tier+name+sha256(body), before it first steers un-confirmed; user-tier skills steer immediately.
- **Gated to Claude-backed sessions only**: an `agent/pre-step` listener re-derives the agent's *current* model provider via `currentProviderOf()` every step and registers/disposes the whole command set (plus `/refresh-skills`, registered on gate-open regardless of skill count so it stays reachable even when the initial scan finds none) as the provider crosses into or out of `anthropic`. The command handler re-checks the provider again at invocation time, closing the one-step lag between a provider switch and the next gate tick. Switching a session's model away from `anthropic` mid-conversation removes the commands again — they are re-evaluated, not decided once at mount. Claude Code Skills are authored against Claude's own conventions and do not silently apply to a DeepSeek-backed agent.

### Error handling

- `claude` binary missing/not on PATH: discovery returns an empty list with a clear "Claude Code CLI not found" message, not a crash.
- Transcript JSONL missing, unreadable, or its shape has drifted: import fails loud with a specific error, never a silent partial or garbled import.
- Malformed or frontmatter-less `SKILL.md`: skipped with a logged warning; the rest of the scan still completes — this is foreign, best-effort discovery over files DSH does not own, not DSH's own configuration.

## Alternatives considered

- **Live-attach bridge (JSONL tail + cross-session messaging socket).** Rejected: couples DSH continuously to two surfaces Anthropic's own docs describe as internal/undocumented, for the life of every attached session, rather than once at import time.
- **Byte-perfect structural import into DSH's own session-log event types.** Rejected: no clean mapping exists from Claude Code's tool-call content blocks onto `SessionEventMap`; would need an extensive, version-fragile translation layer and likely a format-version bump for a foreign event shape.
- **Plain-text-only import, dropping tool call/result content entirely.** Rejected in favor of rendering recognized tool blocks as readable text summaries: nearly as simple and robust, but preserves more of what Claude Code actually did before the import instead of losing it outright.
- **Headless relay (`claude -p --resume <id> --output-format json` per message) instead of a one-time import.** Rejected: this is a genuinely documented, stable interface, but it is not "continue in DSH" — it keeps every subsequent turn dependent on the Claude Code CLI and could conflict with the same session running or attached elsewhere.
- **Ungated skill commands (available regardless of the session's model).** Rejected: Claude Code Skills are authored against Claude's own conventions; surfacing them unconditionally risks a DeepSeek-backed agent receiving instructions written for a different model's behavior.
- **Streaming the Running/Done picker in incrementally as `claude agents --json --all` produces results, instead of grouping/sorting the full list once it resolves.** Rejected: that CLI command has no incremental data source to stream from — it prints its full result as one atomic JSON array only at process exit — so there is nothing to attach an SSE-style progressive render to; the discovery call already resolves once with the complete list, and grouping/sorting that list client-side is strictly simpler.

## Consequences

- A user can open "Import from Claude Code" in DSH's session-creation UI, see their `claude agents --json --all` sessions listed grouped into running/done, pick one, and land in a new DSH session whose opening context reflects that Claude Code conversation's prior turns (including readable summaries of any tool calls it ran). The imported session runs entirely on DSH's own agent loop and tools from that point on; nothing it does after creation touches Claude Code, the `claude` binary, or the source transcript file.
- While a session's active model provider is `anthropic`, `/`-typing surfaces that session's Claude Code Skills (from its `cwd` and the user's home skills directory) as commands; switching to a non-Claude model removes them within one `agent/pre-step` tick, and the command handler's own re-check closes the remaining lag at invocation time.
- `claude` being absent, a corrupt/oversized transcript, or a malformed skill file each fail predictably (empty list / loud import error / skipped skill with a warning) without breaking anything else in DSH.
- Claude Code's JSONL transcript format is explicitly documented as internal and subject to change between releases; the parser will need maintenance when it drifts. This is bounded by scope: the transcript is read once at import time, not tailed live, so a format change surfaces as a loud, contained import failure rather than corrupting an in-progress session.
- `claude agents --json --all`'s own output shape is a CLI-surface dependency DSH does not control; a breaking change there degrades discovery to an empty list rather than a crash, per the error-handling section above, but the feature is unusable until adjusted.
- Rendering `tool_use`/`tool_result` blocks as text summaries is a lossy, best-effort translation with no fixed spec; summaries may read awkwardly for tool shapes not yet seen in practice. Accepted because the alternative (dropping them, or attempting full structural fidelity) was strictly worse per the alternatives above.
- The terminal-status allowlist in `session-grouping.ts` is still not verified against the CLI's real status vocabulary beyond `'done'`/`'working'` — a status this codebase hasn't seen yet keeps defaulting to `running` rather than risking a session silently vanishing into the wrong bucket, at the cost of a session that is actually finished sometimes staying grouped as running until its status matches the allowlist.
- Skill-command gating reads the agent's *current* model selection on every `agent/pre-step` tick and again at invocation time, rather than caching it at mount — bought at the cost of that extra per-step and per-invocation check, to close the gap where a decide-once-at-mount implementation would otherwise leak Claude-authored instructions into a later non-Claude turn.
